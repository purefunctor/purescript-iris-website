# Editor demo recordings

This directory records the landing page's editor trailer: one continuous VS Code take captured with Cap, and a Remotion project that renders the trailer over it. These notes extend the repository's [`AGENTS.md`](../../AGENTS.md), whose design constraints and color token rules apply to the trailer too.

It reproduces the native VS Code workflow from the [original recording thread](https://ampcode.com/threads/T-01a0cf38-55ca-765a-a413-2e7de30fe101). It seeds a disposable `iris-website` workspace from this checkout's `src`, `spago.yaml`, and `spago.lock`, using its installed dependencies and Iris on PATH. Never perform recording edits in the website checkout itself.

## Recording

Commands below run from the repository root. The Linux recording environment needs `agent-browser`, FFmpeg, curl, unzip, fontconfig, Xvfb, Openbox, xdotool, the native Electron libraries and Cap. On Debian:

```sh
sudo apt-get install -y xvfb openbox xdotool bibata-cursor-theme \
  libnss3 libxss1 libasound2 libgtk-3-0 libgbm1 libxkbfile1 libsecret-1-0 xauth
bash scripts/editor-demos/editor-setup.sh
bash scripts/editor-demos/cap-setup.sh
amp orb service start iris-demo-code --command 'bash scripts/editor-demos/editor-launch.sh'
agent-browser --session iriscode --cdp 9223 press F11
node scripts/editor-demos/editor.mjs trailer
(cd scripts/editor-demos/trailer && pnpm install --frozen-lockfile && node render-editor.mjs)
```

- Setup pins VS Code 1.139.0, Iris extension 0.1.0, PureScript syntax extension 0.2.10 and Geist 1.7.2. The current take uses Iris 0.1.10. It selects Geist for the workbench and Geist Mono for code, and keeps Iris's diagnostics defaults; the take turns on-change diagnostics on only for its live-diagnostics beat, so half-typed code elsewhere does not flash parse errors.
- [`theme.ts`](theme.ts) generates the editor colors from the site's tokens in `src/global.css` and layers them over Default Dark Modern through the profile's color customization settings, so recordings match the site. Change the tokens or the mapping there rather than editing the profile, then rerun setup and record again.
- [`cap-setup.sh`](cap-setup.sh) installs Cap 0.6.0 in an Ubuntu 24.04 chroot, because its Linux binaries need glibc 2.39, and writes the `/tmp/iris-editor-tools/cap-cli` wrapper that [`cap.mjs`](cap.mjs) runs (`IRIS_DEMO_CAP` can override it).
- Capture is native 1920×1080 at 60 fps through Cap's CLI, which renders a smoothed cursor, click ripples and zoom, and exports H.264/yuv420p MP4 with fast start and no audio. On this CPU-only display Cap drops frames above 1080p (55 fps at 1440p, 11 fps at 4K); `IRIS_DEMO_SCALE=200` or `300` sizes the display for those. Electron's scale factor is 150% by default; this scales the whole application, not just the editor font. Use VS Code's F11 fullscreen, not the window manager's fullscreen, to avoid window borders. Do not apply browser viewport emulation to the Electron session.
- The CLI does not generate zoom itself: `cap.mjs` writes zoom segments from the pointer and keyboard actions that `editor.mjs` logs. Each passing check also logs the uncovered overlays, such as hovers, suggestions, peek views and quick input, and the zoom frames the pointer and those boxes together, zooming less or not at all when they would not fit. A wider framing that contains the current one replaces it from its start, so the camera does not pull back partway through an action. A check whose subject is something else, such as highlighted references, a setting or recoloured code, names it with a script returning elements and is framed on that instead of the pointer. Wrap stretches that should stay unzoomed, such as changing a setting or scrolling, in `overview`. Clicks are held for 50 ms because Cap polls the pointer every 16 ms.
- Scenarios leave the pointer where the work is rather than parking it, except that typing first moves it quickly into nearby negative space, preferably below and to the right, because the recording keeps it visible while typing. Scroll with `smoothScroll` rather than jumping.
- `editor.mjs trailer` records the trailer's one continuous take, following [`editor-screenplay.md`](editor-screenplay.md): Act I reads `Website.Landing.Index`, `Website.Landing.Demos` and `Website.Landing.Benchmarks`, and Act II renames a type variable in `Benchmarks` and a `CopyButton` constructor across modules, then writes the demo section's chapter selection handler. Staging stubs that handler and its `for_` import in the seed. Every beat asserts its result, and after the take the saved files must equal the repository's with the take's renames applied, so moving or renaming that code means updating the scenario and the screenplay together. Setup and capture use `/tmp/iris-editor-tools` by default (`IRIS_DEMO_HOME` can override it). Setup resets only that disposable workspace and profile; stop VS Code before rerunning setup, and rerun it so that the seed matches the checkout.
- `beat` marks where a feature starts, after holding the previous result for 500 ms. It does not move the camera itself, but Cap's zoom planner starts a new framing there, so one feature's framing never widens to take in the next; the camera pans between them instead. Cap's zoom planner holds each framing for three seconds and across pauses of up to two seconds. Keyboard work is framed on the editor's text cursor, not the pointer, and `quickInput` frames quick input as it opens, before anything is typed into it. Each scroll is one swift ease-in-out (`smoothScroll`) that the page animates itself, a synthetic wheel event per frame, so it lands exactly where it should. VS Code's own smooth scrolling is off in the profile, because it animates each event separately and stutters against the per-frame events; dragging the scrollbar and turning the wheel notch by notch both look choppy in the recording. A check that finds nothing in view leaves the framing as it is; only `overview` zooms out. `beat(slug, { continues: true })` starts a feature without a new framing, for one that carries on where the previous ended, as rename does after workspace symbols. Keys pressed with `browser('press', …)` rather than `press` are not framed, for keys whose text cursor is somewhere the camera should not go. `steadily` holds one fixed framing over a stretch, whatever moves inside it: Act II writes the handler from automatic imports to diagnostics under one 1.3× framing of the gutter and the handler, with the import scrolled into the same framing and back. Semantic highlighting is switched on by writing the profile's settings, and the script logs the screen boxes of the tokens it recolours, grouped by role, for the trailer's captions; it fails if a recoloured token has no caption.
- A failed take can leave unsaved edits, a refactor preview or a native dialog behind. Staging saves and closes editors and closes panels, and refuses to start while a native VS Code dialog is open, because those take all input and are invisible to CDP screenshots; capture the X display with FFmpeg to see one.
- The take is also exported on its own, at 85% of captured speed with a one-second final-frame hold and CRF 28, as a review copy that is not published. `node scripts/editor-demos/cap.mjs trailer --zoom 2` re-exports it with different effects without re-recording it. `IRIS_DEMO_RECORDER=ffmpeg` captures the X display with FFmpeg instead, with the system cursor and no zoom.
- Beside the take, `editor.mjs` writes `trailer.pace.json`, on the raw Cap export's timeline: where the scripted work starts and ends, each feature's beat, and the captions.

## Trailer

The landing page plays one trailer from `public/editor-demos/`. [`trailer`](trailer) is a Remotion project with its own pnpm workspace and lockfile, so the site's install and deployment never fetch Remotion. It imports `src/global.css`, `Backdrop.js` and `Logo.js` from the site, so the cards use the site's tokens, Geist, the logo and the hero's dot lattice; change those there rather than copying values into the trailer.

- [`chapters.ts`](trailer/src/chapters.ts) holds the running order and each feature's generic name, which must match the take's beats; its two acts group the landing page's chapter list. [`editor.ts`](trailer/src/editor.ts) plans the take as one continuous, full-screen shot between the opening and end cards, at recorded speed throughout. Cap's zoom stays as recorded.
- The only overlays on the take are the semantic highlighting captions, which fade in place rather than sliding; there are no divider screens. Do not caption feature names over the take, because the landing page's chapter list and the caption under the player already name each feature. The end card's lockup matches the opening's.
- `node render-editor.mjs` copies the raw take in, renders a 4K master at CRF 12 (twice the composition's size), and encodes from it at 1080p60 with fast start: `out/trailer-av1.mp4` (SVT-AV1, CRF 52, about 40% smaller), the `out/trailer.mp4` H.264 fallback (CRF 28, High profile, level 4.2), and the `out/trailer.webp` poster from the opening lockup. It prints each chapter's start time. `node render-editor.mjs --encode` redoes only the encodes from the last master, and `node render-editor.mjs --review rename,completion` cuts those features, by slug, from the last encode into `out/review`, so a change can be reviewed without the whole trailer. Copy the three files to `public/editor-demos/`, and update the `at` times in `Website.Landing.Demos`, whose chapter list seeks the trailer. The landing page's player lists the AV1 source first with its `codecs` string, so browsers that cannot decode AV1 fall back to H.264; keep those strings in step with the encodes' profiles and levels.
- `node render-editor.mjs --still 240,1200` renders single frames and `--frames 0-600` a range, for checking a design without a full render; `pnpm studio` opens Remotion Studio after one render has written `public/manifest.json`.
- Review the render frame by frame around every transition and the captions, check its dimensions, frame rate and decode with ffprobe/FFmpeg, and inspect playback and chapter seeking on the landing page at desktop and mobile widths. Production serves the trailer without Range support, so check seeking in the production preview as well as in development. Keep raw takes, Cap projects, rendered masters and diagnostic snapshots out of Git.
